## Scope

Closes learniq round-1 finding 9.11 ("Parents maintain their own contact
data and preferences") using capability already shipped on `development`:
`change-proposal-queue` (PR #604) already gives any portal subject a
propose/accept/reject/withdraw queue, and `portal-writer-crossref-guard`'s
underlying mechanism (`portal-create-cross-refs`, PR #607) already closes
the write-side ownership risk the finding flagged. The two real gaps were a
read endpoint (a proposer had no way to list their own queue) and the
frontend (no component rendered a `propose-change` action at all). This PR
adds `ProposalService::mine()` / `ProposalController::mine()`
(`GET /portal/api/proposals/mine`, filtered server-side by the bearer's own
`subjectRef`) and a `ProposeChangeForm` + `ProposalQueue` in the portal
SPA's detail block, so a guardian can propose a correction, see it queued,
and withdraw it.

## Not stacked, by design

The brief asked for this to stack on a `portal-writer-crossref-guard`
branch. Investigation before writing any code found that fix already fully
shipped and merged (`portal-create-cross-refs`, PR #607, 2026-09-18,
commit `809fde2`) — a generic `crossRefs` declaration + `PortalCrossRefGuard`
that resolves every declared reference through the same scoped read the
portal uses to show a subject one of their own objects, refusing with 403
`cross_ref_refused` otherwise. `git diff origin/development
fix/portal-writer-crossref-guard` is empty; no PR was opened for it (nothing
to merge). This branch is cut directly from `origin/development` instead,
which is equivalent to stacking on a no-op branch.
