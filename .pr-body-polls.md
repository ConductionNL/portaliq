A staff member creates a poll (a question with fixed options) addressed
to one audience within one organisation. Every portal subject of that
audience sees it, answers once, and may change their answer while it is
open.

## Deliberate scope cut: no per-group targeting

`change-plan.md`'s description names "per group" targeting, matching
`leaf-integrations`' PollsProvider's own Session/Cohort scoping. That
needs a `via`-style join to group membership — the same mechanism
`portal-contribution-contract`'s "One-hop via join scoping" already gives
a CONTRIBUTED collection from another app, but not a schema portaliq owns
itself. Generalising that join is real, separate design work this
NICE-priority row does not need answered to deliver its core value: a
parent audience can now be asked a question and answer it. Named
explicitly as a follow-up in `proposal.md`'s Motivation, not silently
dropped — matching the finding's own "adjacent, does not close this row"
candor about the nearest existing hit.

## What changes

- `portalPoll` / `portalPollResponse` schemas (register bumped 0.26.0 →
  0.27.0; `PortaliqRegisterConfigTest` updated to match, per its own
  established version-bump convention).
- `PollService` / `PollController`, following `ProposalService`/
  `ProposalController`'s exact conventions.
- `POST /apps/portaliq/api/polls` (staff, `NoAdminRequired`).
- `GET /portal/api/polls` (bearer-scoped — audience + organisation from
  the resolved subject, never the request; each poll carries only the
  bearer's own response).
- `POST /portal/api/polls/{id}/respond` (bearer-scoped, idempotent — a
  second call from the same subject UPDATES their existing response
  rather than creating a duplicate; refused on an unknown option or a
  closed poll).
