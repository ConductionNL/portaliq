## Scope

Closes learniq round-1 finding 14.4 ("Notification settings per role and
channel", `learniq-round1/compare/findings.md` / `change-plan.md` in
ConductionNL/market-intelligence). studytube lets an admin set per-role
which notifications a Teammanager receives; docebo offers a channel matrix
(Email/Platform/mobile push/Slack); talentlms sends per event category with
configurable recipients. Learniq's own `LearniqNotificationSettings.vue` is
per-user only; portaliq had no notification preference of any kind.

A `portalAccount`'s own `audience` is already its role — one account, one
role — so a per-account channel opt-out IS "per role" without a separate
role-keyed settings table.

## Deliberate deviation from the corpus's sizing

`change-plan.md`'s portaliq row classifies this as `kind: config`, size S.
Reading the actual dispatch mechanism this session
(`openspec/specs/supplier-portal/spec.md`'s "Manifest notification rule
keys drive an out-of-band email", `NotificationDispatchService`,
`NotificationDispatchJob`) found there is exactly ONE channel today
(email) and NO opt-out at all — every account with an email is emailed on
every matching trigger, unconditionally. A schema-only change would add a
field nothing reads. Reclassified to `kind: code`, still small (one schema
property, one self-service param on an existing route, one guard clause in
the dispatch job) — an unattended-session call, recorded in
`proposal.md`'s Motivation rather than left implicit.

## What changes

- `portalAccount.notificationChannels` (object, today just `{"email": bool}`).
- `PortalSelfServiceService::updateDetails()` / `PortalAccountSelfController
  ::updateDetails()` gain an optional `emailNotifications` param, threaded
  through the EXISTING `PATCH /portal/api/identity/details` route — no new
  route.
- `NotificationDispatchJob::doRun()` skips an opted-out account the same
  way it already skips a non-matching rule key (no send, no
  `portalNotification` row) — deliberately NOT the same way it handles a
  missing email address (which logs a `failed` attempt and counts toward
  `needsAlternativeContact`), because an opt-out is a choice, not a
  delivery failure. See `design.md` D-1/D-2 for the reasoning.
- Fail-open default: a missing `notificationChannels` key (every account
  that existed before this property did) is treated as opted in, so no
  existing account's behaviour changes.

## Out of scope (see proposal.md)

- A portal SPA control for this preference — the API is real and usable,
  but a settings-page UI is its own reviewable unit of frontend work.
- Any channel beyond email (push waits on `push-notifications-quiet-hours`,
  a separate change, actually adding a second channel).
