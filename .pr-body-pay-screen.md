## Scope

A guardian sees their school contributions in the portal and pays one from its row: the portal shows the voluntary notice, asks to confirm, forwards shillinq's existing `pay` action for that one row and sends the browser to the checkout shillinq returns. Portaliq holds no amount, no invoice state and no provider; it gains a generic endpoint row action (a row-scoped forward that reads the row under the subject's scope before it forwards) that filinq's sign action can use too.

Decision D30 (learniq round 1 decisions, 27 September): "The portaliq pay screen for a school contribution is built now on shillinq's contribution invoices." Consumes shillinq #1704 (contributions raise, `parent` manifest) and shillinq's `portal-payment-initiation` receiver.

## What changes

- `RowActionResolver`: `rowActions` may name an endpoint action that declares `rowField` (entries as string ids or `{id}` objects; the singular `rowAction` shillinq ships is read as one more entry). Optional `rowWhen: {field, in}` limits the rows. Optional collection `noticeField`.
- `PortalRowActionController` + route `POST /portal/api/collections/{register}/{schema}/{id}/actions/{actionId}?collection=`: subject, row action of the collection, trust of collection and action, instance-local endpoint, scoped read of the row (404), `rowWhen` (409), body = `fields` whitelist + proven row id under `rowField` (+ `subjectField`), audit, forward, relay. Never a raw client body.
- SPA: per-row button only where `rowWhen` matches, `RowActionConfirm` with the notice, `runRowAction`, redirect to an absolute `https:` URL only, one message per answer class, notice on the detail card.
- Docs: `docs/operations/row-actions-and-payments.md` (parent, operator, app author), README route row.
- This builds D1 and D2 of the open change `case-actions-sign-a-document` in its words; that change keeps its dialog and its assertion claim.

## Shillinq follow-up needed before the button appears

Shillinq's `pay` action carries no `rowField`, and portaliq cannot guess the body key without shillinq knowledge (a wrong guess shows a button that always fails). Until shillinq adds these keys the portal shows today's list without a pay button. In `lib/Portal/PortalContributionProvider.php`:

```php
// on the pay action
'rowField' => 'invoiceId',
'rowWhen' => ['field' => 'state', 'in' => ['issued', 'partially-paid', 'overdue']],
// on the parent salesInvoices collection (forParents())
'noticeField' => 'invoiceNote',
```

and drop `rowAction` from `paymentRequests` (its row id is a payment request, not an invoice). Operator setting: `portal_payment_redirect_url` in shillinq, pointing at the portal.
