## Scope

Closes learniq round-1 finding 10.3 ("Mobile app (iOS, Android) or PWA for
parents", `learniq-round1/compare/findings.md` / `change-plan.md` in
ConductionNL/market-intelligence). aula, wilma, edupage, iserv, parentcom
and eleven more all offer a native mobile app; portaliq had zero hits for
a mobile app or a PWA.

**No native app** — `tier-b-and-sibling.md` explicitly did not recommend
that commitment (two more codebases, app-store accounts, review cycles).
Instead: the existing portal SPA becomes installable — a web app manifest,
a scoped service worker, a dismissible install control.

## What changes

- `PortalManifestController::manifest()` / `::serviceWorker()`, both
  `#[PublicPage]`. The manifest is resolved through the SAME
  `PortalRuntimeConfigResolver` `PortalPageController::index()` already
  uses, from the identical `?org=`/`?portal=` query, so the manifest and
  the page installing it can never name two different tenants.
- `templates/portal.php` links its own manifest via `Util::addHeader()`
  (confirmed this session as the correct NC API for a custom `<head>`
  element on a `RENDER_AS_BASE` template).
- `src/portal/serviceWorker.js` — plain, unbundled JS (deliberately NOT a
  webpack entry: `/js/` is entirely gitignored build output, so a
  hand-written service worker cannot live there and stay reviewable in
  version control). Served through the controller reading its contents.
- `src/portal/main.jsx` registers it after mount, fail-silent.
- `src/portal/App.jsx` gains a dismissible install control:
  `beforeinstallprompt` → store + prevent default → own banner →
  `.prompt()` on click → hides on `appinstalled` or dismissal.

## The one security-relevant rule (design.md D-1)

`serviceWorker.js`'s fetch handler checks the request path against
`/portal/api/` FIRST, before any cache logic runs, and forwards it to the
network unconditionally when it matches (or when the path isn't on the
small shell-asset allow-list). This ordering is the whole property: an
unlisted or unanticipated path is uncached BY CONSTRUCTION, not by an
exclusion rule that has to stay correct forever. Caching an authenticated
`/portal/api/` response would let a later, differently-authenticated load
of the same URL serve someone else's data.

## Out of scope (see proposal.md)

- Any native iOS/Android app-store app.
- Per-organisation icon/`theme_color`/`background_color` in the manifest
  — one shared icon (`img/app.svg`) and neutral colours ship instead;
  deriving an accurate per-org colour needs reading `theme.css`'s
  `--nldesign-color-*` token resolution, not investigated this session.
- Offline reads of any portal data — this is shell caching for
  installability, not an offline-capable app.
