# Design: wmebv-submission-receipts

## Problem

WMEBV makes three post-submit side-effects legally mandatory (receipt, data
copy, proof log) and one pre-submit constraint (form data-minimisation). The
create-action pipeline currently does none of them. The design must add them
*without* making the domain submission itself hostage to a side-effect: a citizen
who submits a bezwaar must never have that submission fail because the receipt
message could not be written.

## Where the receipt is generated

The authoritative write is the domain object create inside
`ContributionController::create()` (and the create branch of `action()`). The
receipt is a *follow-on* to a successful create, generated by a new
`SubmissionReceiptService`:

1. `create()` writes the domain object (unchanged; authoritative).
2. On success, `SubmissionReceiptService::record()` is called with the
   subject, organisation, appId, actionId, and the **already-whitelisted** field
   map (the same array the writer persisted — never the raw request body).
3. It writes a `portalMessage` (the ontvangstbevestiging) and a
   `portalSubmission` (the proof log), linking them via `receiptMessageRef`.

The whitelisted map is the WMEBV "copy of submitted data" — it is exactly what
the government accepted, with client-supplied non-whitelisted keys already
stripped, so the copy cannot leak fields the server ignored.

## Failure is never silent, never lossy

`record()` runs after the create has already returned success to OpenRegister.
Its own failures are caught and never propagated to the create response:

- If the domain create succeeded but the `portalSubmission` write failed, the
  create still returns 200. The failure is logged (`ILogger`) and, where the log
  record itself could be written with `deliveryStatus: failed`, it is — so a
  retry job can find it.
- `deliveryStatus` on `portalSubmission` is the retriability signal:
  `pending` → `delivered` (receipt written) → or `failed` (receipt write threw).
  A later retry (out of scope here; hook noted for `portal-notifications-dispatch`
  background job) can re-attempt `failed` rows.

This is the same fail-*open-for-the-primary-write*, fail-*closed-for-security*
posture the rest of the edge uses: security checks fail closed, but a compliance
side-effect must never destroy the user's primary action.

## Data-minimisation guard

`PortalManifestNormaliser::normaliseFieldConfigs()` already drops `fieldConfigs`
for fields outside the action's `fields` whitelist. WMEBV adds a second gate on
the `required` flag specifically: `required: true` is honoured only when the
field is in the action's **schema `required` set** (genuinely mandatory).
Otherwise the flag is dropped (the field stays optional — the safe,
data-minimising direction). The normaliser reads the schema via the existing
`PortalSchemaReader`; if the schema cannot be resolved, `required` is dropped
fail-closed (never elevated on a guess).

## Retention

`portalSubmission` is an evidentiary record. Per the fleet convention
(Archiefwet: consume OpenRegister's records-management retention, do not rebuild),
retention/TTL is expressed via OR's `_retention` transient rather than a bespoke
purge in portaliq. This change only writes the record; retention policy wiring is
an OR-side concern noted for the operator.

## Article-number caveat

The Awb article citations in the proposal are indicative. Before implementation,
the exact article numbers MUST be reconciled against the consolidated BWBR0048252
text (the WMEBV renumbered several Awb afdeling 2.3 articles). The obligations
themselves — automatic receipt, data copy, proof log, form data-minimisation —
are stable regardless of final numbering.
