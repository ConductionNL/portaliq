# Tasks: nldesign-theme-integration

## 1. Adoption — a portal picks a real token set

- [x] 1.1 Read the catalogue rather than probing the filesystem for `css/tokens/<theme>.css`. Resolved server-side from the theme app's `token-sets.json` — the same file `CatalogController` serves — because the renderer runs for ANONYMOUS visitors and the endpoint is deliberately not public (see 1.2).
- [x] 1.2 Establish that the catalogue endpoint is safe for an ANONYMOUS caller, not merely a non-admin one. **It is not, by design.** `CatalogController::tokenSets()` is `#[NoAdminRequired]` and deliberately not `#[PublicPage]`: its docblock states that exposing admin-uploaded custom sets to anonymous traffic "would be a new information-disclosure surface with no consumer need". The route was left alone; the public renderer reads the catalogue from disk, and the authenticated admin UI remains the endpoint's consumer.
- [x] 1.3 `PortalThemeResolver` resolves `portal.theme` against the catalogue and returns null when the id is unknown. A file present on disk but absent from the catalogue — a generated variant, a leftover — is no longer adoptable.
- [x] 1.4 Surface the resolvable set to the admin UI. **Done** — `GET /api/themes` serves the catalogue and the admin settings page lists all 46 sets with their ids. `portal.theme` was free text against a catalogue nothing in this app displayed, so choosing one meant knowing an id, and getting it wrong renders the portal UNSTYLED — deliberately, and silently. The endpoint is `#[NoAdminRequired]` and NOT public, matching the theme app's own posture: the catalogue includes admin-uploaded custom sets, and its own docblock records that exposing those anonymously would be an information-disclosure surface with no consumer need.
- [x] 1.5 Test: an unknown id renders UNSTYLED and does not fall back. Covered per branch: uncatalogued file, catalogued-but-missing file, and an unreadable catalogue (fails closed).

## 2. Generation — dark variants and fonts

- [x] 2.1 ~~Link `css/tokens/dark/<id>.css`~~ **Withdrawn on measurement, and the withdrawal is the deliverable.** Implemented, rendered and measured twice: the artefact as generated changed **0 of 1,152,000 pixels**; after `nldesign` was fixed (see 2.5) it changed 53% and left **10 of 11 text nodes below 4.5:1**. This site has no token-driven surface layer. Backed out, with the numbers recorded in `templates/site.php` and pinned by a test so re-adding the line is deliberate.
- [~] 2.2 Respect the instance's dark-mode toggle. **The mechanism is right and the artefacts are not — measured a second time, and withdrawn a second time.** No second switch was ever needed: the generated dark file is itself wrapped in `@media (prefers-color-scheme: dark)` and scoped `body:not([data-theme-light])…`, which is exactly what `CssInjectionService` relies on, so linking it unconditionally honours both the OS preference and an explicit theme choice. It was linked, measured, and backed out — see 2.4 for the numbers and the cause.
- [x] 2.3 Consume the theme app's fonts. **Done, and the task's premise was two different problems wearing one name.** `FontController::css()` is `#[PublicPage]` — a CSS `url()` font load carries no CSRF token and must work before any session — so the site now links it directly and an administrator's UPLOADED faces reach a public portal with no font pipeline in this app. It is empty (0 bytes) until someone uploads one, so linking it unconditionally costs a portal with no custom fonts one cached request. **It does NOT replace `nlds-fonts.css`**: that file re-declares the VENDORED design system's own faces because the captured stylesheets carry root-relative `url()`s that resolve against the origin and 404 from this app's path — measured previously as four requests, four 404s and the whole portal drawn in Arial. `FontService` manages uploaded faces; those are a different set of fonts solving a different problem, and dropping the hand-written declarations would take the design system's typography with it.
- [~] 2.4 Test: a `prefers-color-scheme: dark` visitor gets the dark variant. **Tested, and the answer is no — with an exact cause this time.** 2.6 was the recorded prerequisite, so the link was tried again and measured on `conduction-klant`:

  | | light | dark |
  | --- | --- | --- |
  | surfaces that changed | — | **0 of 8** |
  | text below AA | 0 of 38 | **19 of 38** |
  | worst | — | **1.03:1**, `#141414` footer text on `#0a172f` |

  Strictly worse than no dark mode, on a public government portal, so it is backed out again.

  **THE CAUSE IS NOW EXACT, and it is the same shape as this app's `--navigation-bar-height` finding: an alias resolves where it is DECLARED.** The generated dark file scopes its overrides to `body` and redefines base colours there, while the light set declares the aliases above them on `:root`. Read back live in a dark-scheme browser:

  ```
  --c-white                              root #FFFFFF   body #141414
  --conduction-color-background-default  root #FFFFFF   body #FFFFFF
  --utrecht-document-background-color    root #FFFFFF   body #FFFFFF
  ```

  So the surfaces stay white while the direct text colours darken — which is precisely how a footer reaches 1.03:1. **No change in this app can fix it**: re-declaring the bridge on `body` still reads an alias that resolves at `:root`, and the chain breaks at its first `:root`-declared link whichever end it is read from. The prerequisite is now the theme app's — the dark sets must redefine the ALIASES, or scope their block to `:root` inside the media query. That is defect 1 of ConductionNL/nldesign#353, recorded as fixed in the generator but **not present in the artefacts this instance ships**, so the remaining work is to regenerate all 45 of them and re-run this measurement.
- [x] 2.5 Fix the generator in `nldesign` — three defects found by chasing the 0-pixel result, each of which produced output that reads as a successful run (ConductionNL/nldesign#353): `var()` aliases were never darkened (an alias declared on `:root` resolves there, and the dark block scopes to `body`, a descendant — so only 13 of 600 `--utrecht-*` tokens survived); text was classified as surface outside the `--nldesign-*` naming convention; and `GENERATOR_VERSION` was stamped into every header and read by nothing, so an algorithm fix regenerated **0 of 41 sets**.
- [x] 2.6 Give the site a token-driven surface layer. **Done, and it is an indirection rather than a dark theme.** First MEASURED which elements actually paint: eight surfaces, every one of them a literal colour from the vendored NLDS sheets that never asks a token anything — the page and its container (`#fff`), both header bars and the primary nav (`#fff`), the category cards (`#fff`), the tinted card and the hero's search box (`#eef1fa`). That is why a dark set could change 0 pixels and, once the generator was fixed, 53% of them badly. Each now resolves `--nldesign-site-{surface,surface-raised,surface-sunken}` → `--utrecht-document-background-color` → the literal, so a generated dark variant reaches the page without anyone hand-mapping it. **Verified by moving them**: setting `--utrecht-document-background-color` alone repaints all eight; before the fix it repainted none. **One surface refused at first** and the reason is worth keeping — `.pq-site` is painted by a Vue SCOPED style injected at runtime by `style-loader`, so it lands after every linked sheet and wins on ORDER, not specificity; `site-theme.css` cannot out-rank it, so the scoped rule now defers into the same chain instead. **Light mode is provably unchanged**: every fallback is the colour measured on the page beforehand, and re-enumerating all eleven painted surfaces after the change returns byte-identical colours and areas. `npm run check:surfaces` passes 12/12. **Text colour is deliberately NOT included** — `--utrecht-document-color` is `#1b1b23` while this page's body text computes to `rgb(0, 0, 0)`, so painting it would be a visible change disguised as a no-op refactor; it belongs with the dark variant (2.2/2.4), where the surfaces move and the text must move with them.
- [x] 2.7 **Stop shipping the design system's CSS twice.** **Done — 393.6 KiB to 358.3 KiB.** Nine of the ten `@utrecht/*-css` imports removed from `main.js` (deleting every injected `<style>` on a rendered portal changed exactly ONE computed property — the skip link's `position` — so that one import stays), and the library's dist CSS excluded by a four-line local loader rather than a new dependency. Worth recording: the dist-CSS exclusion alone changed the output by ZERO bytes, a 1.65 MB module left the module graph and the bundle did not move. A module list is not a byte count. Measured on the rendered Conduction portal: 287 KiB of CSS is injected from `portaliq-site.js` by `style-loader` — `.utrecht-heading-1`, `.ac-c-navigation__primary`, `.utrecht-skip-link` and the rest — while `templates/site.php` ALSO links twelve stylesheets carrying the same `ac-*` / `utrecht-*` system. That injected CSS is the bulk of a 393.6 KiB bundle whose budget is 400 KiB (e2e S18, measured on transferred bytes), which leaves 6.4 KiB of headroom for every future feature: adding the contributed-page renderer alone took it to 415.6 KiB and the work had to be backed out. Extract it (`mini-css-extract-plugin`, or drop the imports the linked files already cover) and link one file instead. This is the prerequisite for §6 and for anything else the site renderer grows.

## 3. Contrast and compliance — at adoption time, not after a review

- [x] 3.1 Evaluate the adopted theme's contrast and record the verdict. **Done** as `PortalThemeContrast`, which calls the theme app's own `ContrastService` IN PROCESS rather than over HTTP — the controller wrapping it needs a session, and a second implementation of a contrast ratio in this app would be a second answer to the same question. The verdict travels with the catalogue entry, so it is visible where a theme is CHOSEN rather than in a review weeks after a portal went live wearing it.
- [x] 3.2 Warn on a theme failing AA for the surfaces a portal paints. **Done — warn, never refuse**: the failing token, its measured ratio and the surface are named, because that is something an operator can act on, while blocking adoption would be this app deciding a municipality may not use its own brand and would be worked around by editing the record directly.

  **THE FIRST VERSION REPORTED 46 OF 46 SETS PASSING WITH 43 OF THEM UNMEASURED**, and that is the finding worth keeping. It returned `passes: true` whenever it found no failures — which is also exactly what a set declaring none of these tokens produces. The verdict now carries `measured`, and `evaluated` requires it to be non-zero, so the admin table shows "not checked — this set declares none of the surface tokens" for those 43 instead of a clean bill of health. A thing not measured must never be subtracted as though it passed.

  **The hero band is deliberately absent from the static check, and that is also a finding.** It paints itself `#21468B` on the Conduction set, but no `--nldesign-hero-background` exists in any shipped set — the colour comes from the vendored `.ac-hero` rule reading the theme's palette, so there is no token to hold a text colour against. Listing it with a token that does not exist would have made this check silently skip it and still report a pass; it is measured on the RENDERED page by `tests/site-surfaces.spec.mjs` instead.
- [x] 3.3 Add the portal's own rendered surfaces to the check, walking to the first ancestor that PAINTS a background. Comparing against the nearest NAMED band produced a false failure in this codebase once already, and the "fix" for it made a working form invisible. **Done** as `tests/site-surfaces.spec.mjs` (`npm run check:surfaces`): ten page/width combinations across both demo portals, walking to the first ancestor that actually paints and skipping scrims below 30% alpha. It also COMPOSITES translucent text over that backdrop before measuring — without it `rgba(255,255,255,0.22)` scored 17.85:1 against a navy band, and a deliberate break passed the check.
- [x] 3.4 Test: a deliberately low-contrast token set is rejected/flagged; a compliant one passes. **Done** as the self-test in `tests/site-surfaces.spec.mjs`, which runs on EVERY invocation before any page is judged: it injects a translucent low-contrast colour, a second `h1` and a 3000px element into a real rendered page and demands each be detected, refusing to report a pass otherwise. Proven by blinding the probe to the alpha channel — the defect this file first shipped with — which makes the self-test fail and the run exit non-zero. Injection happens in the browser, never in the token files, so a run that dies halfway leaves the repo clean.

## 4. Sharing — adopt a theme that came from elsewhere

- [x] 4.1 Consume `NlDesignThemeShareableConfigType`. **Done** as `PortalSharedTheme::adopt()`, which reads a bundle through the theme app's own deserialiser when it is registered and falls back to the bundle's plain `declarations` map otherwise — a bundle is data, and refusing to read one because an optional helper is missing would make adoption depend on which services happen to be wired.
- [x] 4.2 Route every shared set through `CustomTokenSetValidator` before it can be stored. **Done, and validation is not optional**: with the validator unavailable, NOTHING is adopted. Failing open there would mean storing another instance's declarations unvalidated in exactly the circumstance where it matters most. A `null` return is treated as a HARD REFUSAL rather than as "nothing to adopt" — the validator's own contract says null means a forbidden construct, and a caller that only checks whether the accepted list is empty turns a refused hostile bundle into a silent no-op.
- [x] 4.3 Decide what happens when a shared theme is withdrawn. **Decided: ADOPTION COPIES, IT DOES NOT LINK.** A link would mean another instance can change, or remove, what a live government portal looks like at a moment nobody there chose — and removal is precisely the silent loss this task forbids. Copying the accepted declarations into the portal's own `tokens` makes adoption a decision with a result: the portal keeps rendering exactly what it was adopted with, and a withdrawal upstream is something an operator is TOLD about rather than something that happens to their visitors. Documented in the spec's new theming requirement and in the `nldesign` docs page (5.1).
- [x] 4.4 Test: a hostile shared set is refused, visibly. **Done** — five hostile shapes (`url()`, `expression()`, `javascript:`, `@import`, markup) each asserted to adopt nothing AND to produce a refusal that NAMES the offending declaration, because an empty refusal string is one an operator can neither act on nor tell from a no-op. A bundle with nothing adoptable is refused rather than adopted empty, for the same reason: a portal that adopted nothing renders unstyled, and "the theme did not apply" is the one outcome indistinguishable from "the theme is subtle".

## 6. Contributed pages — routable, once there is room for them

- [x] 6.1 Route `/diensten/{app}/{page}` to the page a contributing app publishes, rendering its `richText` and `action` blocks, and turn the contributions index entries into links. **Done, once 2.7 made room.** Built, backed out on measurement, and re-landed: at 393.6 KiB there were 6.4 KiB of headroom and this needs ~12; with the duplicated CSS gone the bundle is 370.1 KiB with the feature in. `richText` and `action` blocks render, the index entries are links where a page exists and stay text where none does, and the route is covered by `tests/site-surfaces.spec.mjs`.
- [x] 6.2 Reconcile `anonymous` actions with the endpoint. **The endpoint honoured the flag all along — the RENDERER was posting to the wrong route.** `anonymous: true` is only ever honoured on a `type: create` action, and its route is `POST /portal/api/collections/{register}/{schema}`, where `create()` hands a bearer-less caller to `createAnonymous()`. `ContributionController::action()` is the endpoint-FORWARD route, matched by `authorisedEndpointAction()`, which refuses a create whether or not there is a session — so posting every action there made an accepted submission look like a 401. Proven before writing anything: an unauthenticated `curl` to the collection route created an object (`subjectRef: anonymous`) on the first try. `contributionApi.js` now chooses the route from the action's `type`, `isAnonymouslySubmittable()` requires the type AND the flag (a flag on any other type is a promise no route keeps), and the sign-in notice appears only where a session is genuinely needed. Verified through the UI on La Franken: one POST leaves, to `/portal/api/collections/portaliq/exampleDocument`, with no `Authorization` header, and the row lands. Pinned by `tests/site-contribution.spec.mjs` (`npm run check:site-contribution`, in `check:specs`).
- [~] 6.3 **An "anonymous" submission is stamped with the visitor's Nextcloud UID when they hold a Nextcloud session.** Found while verifying 6.2 and measured, not inferred: the same submission stored `_owner = __system__` from `curl` and `_owner = admin` from a browser holding an admin cookie, while the page it came from says "niet aan een account gekoppeld". The cause is in OpenRegister — `SaveObject::applyOwnerAttribution()` is the sole authoritative setter and overrides a caller-set owner whenever a session exists, so no portaliq-side change closes it. **Fixed upstream: [ConductionNL/openregister#2548](https://github.com/ConductionNL/openregister/pull/2548)** adds `bool $_unowned = false` to `ObjectService::saveObject()`, threaded to the attribution step, defaulting to today's behaviour and forwarded by no controller so no REST request can ask to be anonymised; it stamps the SYSTEM identity rather than an empty owner, because rows with an empty `_owner` are invisible to the REST list path's RBAC filter even for admins (openregister#1617). Five tests, checked against a deliberate break. **The remaining half is one line here** — `PortalObjectWriter::createAnonymousObject()` passes `_unowned: true` once that PR lands. It is deliberately NOT passed yet: an unknown named argument is a fatal, so adding it before the parameter exists would take every anonymous submission down.

## 5. Documentation

- [x] 5.1 Record in `nldesign` that portals are a consumer. **Done: [ConductionNL/nldesign#357](https://github.com/ConductionNL/nldesign/pull/357)** — a docs page covering all four surfaces a portal reads, each with the defect it has already caused: the catalogue read from disk and why, a shipped set being inert without the public bridge, the dark variants' alias-scoping defect with the measured numbers, and the distinction between uploaded faces and the vendored ones.
- [x] 5.2 State what this app consumes instead of "ships NO theming mechanism of its own". **Done — but not in ADR-086, which does not exist.** It is cited by number across these specs and there is no `adr-086-*.md` in `openspec/architecture/` or in hydra's, so there was no §6 to edit. The statement now lives in `openspec/specs/portaliq-cms/spec.md` as its own requirement, with three scenarios: every painted surface resolves through a token, a theme's accessibility verdict travels with the choice, and a shared theme is validated before it can be adopted. The old wording was true of the code and unhelpful as guidance — it said what this app does not do without saying what it consumes, and the consequence was a surface layer that read no tokens at all until somebody measured it.
