# Tasks: portal-traffic-analytics

## 0. Establish the baseline before building anything

- [x] 0.1 Determine what `portalSession` can answer. **Nothing about pages**: its fields are `subjectRef`, `jti`, `issuedAt`, `expiresAt`, `revoked`, `trustLevel`, `audience`, `organisation`, and it exists only for authenticated portal users. Anonymous visitors — the bulk of a public portal — have none.
- [x] 0.2 Determine whether OpenRegister already records page reads. **It does not.** `ProcessingLogService::logRead()` exists and works, but is opt-in per schema via `logReads`, and `lib/Settings/portaliq_register.json` enables it on **0 of 13** schemas.
- [x] 0.3 Determine whether switching it on would answer the question. **No.** It is an AVG verwerkingsregister: object-level, actor-attributed, with no visit, referrer, entrance, exit or ordering. It would also make an accountability record carry analytics traffic.
- [x] 0.4 Determine whether a Docusaurus-rendered portal can be measured server-side. **No.** The plugin fetches content at BUILD time and emits static HTML hosted elsewhere; portaliq is not in the request path when a visitor reads it.
- [x] 0.5 Write the finding down as the reason the design is client-reported. **Done** in `docs/traffic-privacy.md` — all three alternatives with the specific reason each fails, including the one that looks most plausible: switching on `logReads` produces an object-level, actor-attributed accountability record with no visit, referrer, entrance, exit or ordering, and pointing analytics at it would make a *verwerkingsregister* carry traffic.

## 1. The event contract

- [x] 1.1 Define the event envelope: `clientId`, `sessionId`, `sequence`, `name`, `timestamp` (client clock), `pageLocation`, `pageReferrer`, `pageTitle`, plus a bounded `params` map.
- [x] 1.2 Define the shipped event vocabulary — `page_view`, `session_start`, `scroll`, `outbound_click`, `file_download`, `search`, `form_submit` — with the GA4 name for each, so a number here and a number in GA4 mean the same thing.
- [x] 1.3 Define the `portalTrafficEvent` schema in the register.
- [x] 1.4 Test: an event whose `sequence` repeats within a session is rejected — a client that resets its counter must not silently corrupt a journey.

## 2. Per-portal configuration

- [x] 2.1 Extend the `portal` schema: `traffic: { enabled, events[], dimensions[], sessionTimeoutMinutes, retentionDays, consent: { required, preConsentEvents[] }, regionGranularity }`.
- [x] 2.2 Serve the resolved configuration to the client over the public content contract, so the client sends only what the portal asked for. **Done** — `/api/content/site` carries a `traffic` block, PROJECTED rather than relayed: the switch, the permitted events, the session timeout and the consent posture, and nothing else. `retentionDays` and `regionGranularity` are deliberately withheld; they are decisions the server acts on alone and a publicly cacheable endpoint is the wrong place for a portal's retention posture. The published event list is produced by `permittedEvents()` — the SAME function the collector enforces with — so a portal naming an event outside the shipped vocabulary never has it echoed back to a client that would then be refused. The projection lives in `PortalTrafficService::clientConfig()`, beside the collector, so the answer a client is given and the answer the collector acts on cannot fork. **Found while doing this: `portal.traffic` had been declared in `portaliq_register.json` (task 2.1) but never imported, so the live `portal` table had no `traffic` column and no portal could have been configured at all.** `POST /api/settings/load` applied it; the column exists now.
- [x] 2.3 Test: a portal enabling only `page_view` gets exactly that — the collector refuses `search`, and the refusal is counted, not silent.
- [x] 2.4 Test: a configuration field is not merely stored — assert the collector's BEHAVIOUR changes with it. A declared-but-unread config field is this codebase's most repeated defect.

## 3. The collector

- [x] 3.1 `POST /api/traffic` — anonymous, batched, `sendBeacon`-compatible, responding 204 with no body and no cookie.
- [x] 3.2 Resolve the serving portal the same way the renderer does (host, then explicit slug), so an event cannot be attributed to a portal the caller names.
- [~] 3.3 Derive coarse region from the request IP and DISCARD the IP in the same request. Test that no stored field, log line or aggregate contains it. **Half done, and the half that is done is the guarantee.** The address is resolved and dropped inside `TrafficController::collect()`; `PortalTrafficService` takes a region string and has no parameter that could carry an address, so the signature enforces it rather than a comment. Asserted by searching the WHOLE stored record for the address, so passing one as the region would still fail. NO GEO RESOLVER IS WIRED IN: `regionFor()` returns '' rather than a plausible-looking country, because an unmeasured value sitting beside measured ones is worse than an empty field.
- [x] 3.4 Rate-limit per client id and per source, refusing the excess with a counted reason. **Done, and the two limits are not the same control.** Per SOURCE is the controller's `#[AnonRateLimit(120/60)]` — the identifier a caller cannot choose. Per CLIENT ID is `PortalTrafficService::withinRate()`, a fixed 60-second window capped at 300 events, keyed by a hash of the id; it is NOT an anti-abuse control and is not presented as one, because a client id is chosen by the client and anything determined simply rotates it. What it bounds is a client that has gone wrong — a beacon retried without backoff, a handler firing on every scroll frame — filling a portal's own analytics with noise that reads as traffic. It FAILS OPEN with no cache configured, asserted rather than assumed: losing a portal's measurements because its instance has no memcache would present as "nobody visits this portal". Excess is counted as `rate_limited`, and a second client id is proven unaffected by the first one's flood — a limiter keyed on nothing in particular passes the first test and silently stops measuring everyone else.
- [x] 3.5 Refuse an oversized or malformed batch WHOLE — never store a partial batch.
- [x] 3.6 Test: the endpoint is genuinely anonymous. **Done, both halves, live and in PHPUnit.** Live on the rig: a cookieless `curl` to `/api/traffic?portal=lafranken` answered 204 and the row landed with the origin stripped (`/begrippen`) and `_owner = __system__`; the same request against `conduction-klant`, which has measurement off, also answered 204 and stored **zero** rows. Both halves are needed and neither is sufficient: acceptance alone is satisfied by a collector that accepts everything, refusal alone by one that accepts nothing. Pinned as `TrafficControllerTest` — the endpoint declares `#[PublicPage]` + `#[NoCSRFRequired]` + a non-zero `AnonRateLimit`, an anonymous request is recorded, an unresolved portal records nothing, an oversized batch is refused WHOLE and counted, and every outcome — accepted, refused, unknown portal — is byte-identical to the caller.

## 4. Sessionisation and aggregation

- [x] 4.1 Close sessions after the configured inactivity window. **Done in BOTH places, and that is not redundancy.** The client starts a new session after the window; the server splits on it again in `PortalTrafficAggregator::journeys()`, because the session id is chosen by the CLIENT and a browser left open across a lunch break — or a client that reused an id — produces one id spanning a gap no visit spans. Both sides of the boundary are tested: 29 idle minutes is one session, 95 is two.
- [x] 4.2 Reconstruct journeys by `sequence`, not by receipt time. **Done, and checked against a deliberate break** — removing the sort fails exactly the two tests that name it. Events delivered 2, 0, 1 (the shape a retry produces) reconstruct as 0, 1, 2, and the out-of-order aggregate is asserted EQUAL to the in-order one rather than against a hand-written expectation, so the two cannot drift as the aggregate grows fields.
- [x] 4.3 Aggregate: views per page, entrances, exits, transitions, sessions, engaged sessions. **Done**, with two honest limits recorded rather than papered over. *Average engagement time is NOT produced*: this collector stores no dwell timer, and a number computed from event timestamps would be the gap between beacons, not time on page — a plausible figure measuring something else is worse than an absent one. *Engaged sessions* uses GA4's two-page-view limb only, since the ten-second and conversion limbs are unanswerable from what is stored, and it is named as that rather than presented as the same metric. Non-page events (`search`, `outbound_click`) happen ON a page and are excluded from views and transitions. Ties rank by key, so two runs cannot reshuffle a table and make a refresh read as changing traffic.
- [x] 4.4 Delete raw events past the retention window; keep the aggregates. **The decision is done and pure** — `expiredIds()` returns ids rather than deleting, because deciding what is expired and carrying out a deletion have very different blast radii and the decision can then be tested exhaustively without anything being deleted to find out. A row whose age cannot be read is KEPT: deleting what you cannot date is how a retention job becomes a data-loss incident. A retention of zero deletes nothing — "unset" must not read as "expire everything immediately". **The scheduled job that calls it is not wired yet.**
- [x] 4.5 Test: the aggregation job is idempotent. **Done, asserted on the WHOLE result** rather than on one total — a job that doubles one figure and not another survives a narrower check and then quietly reports twice the traffic. The aggregator is pure by construction: it reads no clock, no database and no request, which is what makes both this and 4.2 testable at all.

## 5. The client, shipped with the Docusaurus plugin

- [x] 5.1 A small first-party script: **done** as `src/shared/trafficClient.js` — client id, session and sequence, batched beacons, and only the configured events. Everything it touches is injected (storage, navigator, window, clock, fetch, timer), not for testability alone but because its guarantees are about what it does NOT do, and an absence can only be tested by watching a double that would have recorded the thing happening. It schedules its own flush rather than waiting for `pagehide`: a one-page visit is the common visit, and `pagehide` never fires on a tab the browser discards.
- [x] 5.2 Ship it from `docusaurus-plugin-portaliq` so a statically built portal reports the same events as a server-rendered one, posting cross-origin to its portal's collector. **Done, and cross-origin turned out to be three separate defects that only a real browser on a real second origin could find.** (1) The obvious script URL, `<app>/js/portaliq-traffic.js`, answers **401** to an anonymous caller — every caller a public portal has — and only the deployment-dependent `/custom_apps/…` path serves it; the script is now a declared public ROUTE, `GET /api/traffic-client.js`, so the URL a built site bakes in stays valid. (2) Neither `/api/content/*` nor `/api/traffic` sent any CORS header and `OPTIONS /api/traffic` answered **405**, so a static portal could be BUILT from the contract but nothing on its pages could read it; the anonymous branch of `publicJson()` now sends `Access-Control-Allow-Origin: *` and the collector answers its preflight. (3) **`sendBeacon` always sends with credentials mode `include`, so the browser rejects a `*` response outright** — the client now uses a `keepalive` fetch with `credentials: 'omit'` when the collector is cross-origin and keeps the beacon same-origin, which holds "no credentials, ever" on the server rather than loosening it to an origin echo with `Allow-Credentials`. Verified end to end: a page served from `127.0.0.1:8123` with no console errors, its `page_view` stored against `lafranken` with `_owner = __system__` — proving no session travelled. The plugin ships a `traffic: false` opt-out that emits no tag at all.
- [x] 5.3 Wire the same client into the built-in site renderer, from the same source. **Done** — `src/site/lib/traffic.js` supplies only the environment; every decision stays in the shared module, which is what stops the two renderers from growing different answers to "may we store this". Verified end to end on the rig: three navigations produced three rows with sequence 0/1/2, one session, one client id, the origin stripped from `pageLocation`, and no region (the portal asks for none). A missing page is reported as a page view flagged `notFound` — the routes visitors reach and find nothing at are the ones an editor most needs to see.
- [x] 5.4 Honour Do Not Track and the portal's consent posture before writing anything to browser storage. **Done.** Three DNT spellings plus `globalPrivacyControl` — the successor signal, which carries actual legal weight, and honouring the deprecated one while ignoring the live one has the posture backwards. The permission question reduces to ONE function, `permittedStorage()`: before consent it returns a Map that outlives nothing, so a permitted pre-consent event still carries a client id and a truthful sequence while leaving no trace in the browser. Withdrawing consent clears the id, not just the flag.
- [x] 5.5 Test: with measurement disabled the script sends NOTHING and stores NOTHING. **Done, and proven by breaking it.** Every storage call is recorded by a double, so "stored nothing" means `setItem` was never reached rather than that nothing survived. Checked against a deliberate break (`silent = false`): the first version of these tests still PASSED it, because the consent gate was blocking the send instead of the disabled guard — each case now stands its other gates down so it fails for the reason it names. With that fixed the break produces 5 failures; reverted, 39 assertions pass.

## 6. The Traffic page

> **The Traffic page these tasks describe does not exist in this repo.** Searched
> for it before building anything: there are no placeholder counters, and no
> admin view named Traffic, under any spelling. Like task 6.2 of the theme
> change, the premise is stale. What was genuinely blocking — a portal's figures
> having nowhere to come from — is now closed; the page itself is a separate
> piece of admin UI and is left un-invented rather than half-built.

- [~] 6.1 Replace the three placeholder counters with the aggregates. **The data side is done, the page does not exist.** `GET /api/traffic/summary` serves sessions, engaged sessions, visitors and page views for a portal. It is the ONLY endpoint on this controller that is not public — an aggregate of where a portal's visitors go belongs to whoever operates it — and it is `#[NoAdminRequired]` rather than admin-only, because the people who run a portal's content are not always the instance's administrators. Verified live against real collected traffic.
- [~] 6.2 Show the journey: top entrances, top exits, most-travelled transitions. **Served, not yet shown.** All three are in the summary payload, ranked, with ties broken by key so two refreshes cannot reshuffle a table and read as changing traffic. Verified live: the endpoint reconstructed an actual browsing session's transitions in order.
- [x] 6.3 Say "not measured" for a portal with measurement disabled, and never render an empty chart. **Done, and enforced where it cannot be got wrong.** An unmeasured portal's summary is exactly `{measured: false}` — **no counter keys at all**, not zeroes. A renderer handed `{sessions: 0}` cannot tell "nobody visited" from "nothing was ever collected" and will draw the same empty chart for both, which reads as the first. Withholding the keys means there is nothing to plot by accident, which is stronger than asking every future renderer to check a flag.
- [x] 6.4 Test: a portal with no data and a portal with measurement off differ. **Done, both directions.** A measured portal with no visitors reports `measured: true` with explicit zeroes; an unmeasured one reports the flag alone. The second test is what stops the first from being satisfied by a summary that never reports anything.
